기술 노트/글

잠금 없이 읽는 git status가 클론 직후 3~10배 느렸던 이유

GIT_OPTIONAL_LOCKS=0으로 읽으면 인덱스가 새로 고쳐지지 않는 문제를 커밋 20만 개 저장소로 재고 고친 기록입니다.

2026년 11월 28일블로그 원문

Mac용 Git 클라이언트 Branchlane을 만들고 있습니다. 큰 저장소에서 얼마나 빠른지 숫자로 말하고 싶어서 재 보다가, 저장소를 막 클론한 뒤에는 상태(git status) 읽기가 몇 배씩 느린 채로 계속 남는다는 것을 찾았습니다. 원인은 앱이 일부러 켜 둔 설정 하나였습니다.

잠금 없이 읽는 이유#

Branchlane은 작업 폴더 상태를 이렇게 읽습니다.

터미널
GIT_OPTIONAL_LOCKS=0 git status --porcelain=v2 --untracked-files=all --branch -z

평범한 git status는 읽는 김에 인덱스를 새로 고쳐 쓰려고 index.lock을 잡습니다. 사람이 혼자 쓸 때는 문제가 없습니다. 그런데 Git 클라이언트는 파일이 바뀔 때마다 상태를 다시 읽고, 요즘은 같은 저장소에서 코딩 에이전트가 동시에 git add, git commit을 합니다. 그 순간 앱이 잠금을 쥐고 있으면 에이전트 쪽 명령이 index.lock: File exists로 실패합니다. 실제로 제 Mac의 에이전트 세션 기록을 세어 보니, Git 명령이 막힌 이유 1위가 index.lock이었습니다.

GIT_OPTIONAL_LOCKS=0은 "꼭 필요하지 않은 잠금은 잡지 말라"는 뜻입니다. 상태를 읽기만 하고 인덱스에는 아무것도 쓰지 않습니다.

재 보니#

저장소를 열 때 앱이 하는 일을 엔진 함수 그대로 5번씩 재고 중앙값을 냈습니다. Apple M5 Pro, Git 2.54, release 빌드입니다. 저장소는 커밋과 트리는 모두 받고 파일 내용은 필요한 것만 받는 클론(--filter=blob:none)입니다.

단계 git/git (커밋 8.6만) vscode (커밋 20만, 파일 2.2만)
저장소 열기 4.1ms 3.5ms
참조 읽기 23.7ms 16.3ms
상태 읽기 163.9ms 334.5ms
그래프 로그 2,000개 69.9ms 100.2ms
그래프 배치 2,000개 3.1ms 0.5ms

그래프는 충분히 빨랐는데 상태 읽기가 튀었습니다. 같은 vscode 클론에서 터미널로 평범한 git status를 세 번 돌리면 첫 번째만 0.88초이고, 그다음부터는 0.11초였습니다. 반면 GIT_OPTIONAL_LOCKS=0으로 돌리면 몇 번을 돌려도 처음 속도 그대로였습니다.

원인: 아무도 인덱스를 새로 고치지 않는다#

인덱스에는 파일마다 크기와 수정 시각 같은 stat 정보가 들어 있습니다. git status는 이 정보가 파일과 같으면 내용을 읽지 않고 넘어갑니다. 그런데 클론이나 큰 체크아웃 직후에는 이 정보만으로는 판단할 수 없는 항목이 많이 생깁니다. 파일이 인덱스와 거의 같은 시각에 쓰여서, stat이 같아 보여도 내용이 바뀌었을 수 있는 "racily clean" 항목이 대표적입니다. Git은 이런 파일의 내용을 다시 해시해서 확인합니다.

평범한 git status는 확인을 마친 정보를 인덱스에 다시 써 둡니다. 그래서 두 번째부터 빠릅니다. 잠금 없이 읽으면 이 쓰기를 건너뜁니다. 앱 안에서 스테이징처럼 인덱스를 쓰는 동작을 하기 전까지는, 상태를 읽을 때마다 같은 파일들을 매번 다시 해시합니다. 한 번 내면 되는 비용을 매번 내고 있었던 것입니다.

고친 방법#

상태 읽기가 0.25초를 넘으면 인덱스의 stat 정보만 한 번 새로 고칩니다.

터미널
git update-index -q --refresh --unmerged --ignore-missing

잠금을 피하던 이유를 버리지 않으려고 조건을 붙였습니다.

  • 작업 폴더마다 10분에 한 번까지만 합니다.
  • 이미 index.lock이 있거나 병합·리베이스가 진행 중이면 기다리지 않고 건너뜁니다.
  • 앱 안의 다른 인덱스 작업과는 앱의 잠금으로 순서를 맞춥니다.
  • 에이전트는 보통 자기 작업 폴더(별도 worktree, 별도 인덱스)에서 일하므로 메인 폴더의 새로 고침과 부딪히지 않습니다.

같은 폴더에서 에이전트가 커밋하는 바로 그 순간과 겹치면 에이전트 쪽 명령이 실패할 수는 있습니다. 느릴 때만, 10분에 한 번, 0.2초 남짓이라 이 위험은 받아들였습니다.

git/git vscode
상태 읽기, 고치기 전 163.9ms 334.5ms
새로 고침 한 번 158.7ms 232.3ms
상태 읽기, 고친 뒤 15.6ms 106.9ms

git/git은 10배, vscode는 3배 빨라졌습니다. 저장소를 열고 첫 그래프가 나올 때까지는 git/git이 약 0.11초, vscode가 약 0.23초입니다.

정리#

잠금 없이 읽는 것은 다른 프로그램과 같이 쓰는 저장소에서 옳은 기본값입니다. 다만 "읽기만 한다"는 것은 Git이 읽으면서 해 주던 정리도 하지 않는다는 뜻이었습니다. 어디선가 가끔은 그 정리를 대신 해 줘야 합니다.

터미널에서 직접 확인할 수도 있습니다. 새로 고친 결과는 인덱스에 남으므로, 다시 보려면 클론을 새로 만들어야 합니다.

터미널
git clone --filter=blob:none https://github.com/microsoft/vscode.git && cd vscode
# 몇 번을 돌려도 처음 속도 그대로입니다
time GIT_OPTIONAL_LOCKS=0 git status --porcelain=v2 --untracked-files=all >/dev/null
git update-index -q --refresh
# 새로 고친 뒤에는 빨라집니다
time GIT_OPTIONAL_LOCKS=0 git status --porcelain=v2 --untracked-files=all >/dev/null
